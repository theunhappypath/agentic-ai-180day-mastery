| sample.py      | 1.00       | 2.61                      | +0.0%         | −37.4%         |
| payload.json   | 1.00       | 2.25                      | +0.0%         | −26.8%         |


Worst on: **devanagari.txt, −48.3%** — tiktoken counts 435 tokens where
`count_tokens` returns 842. Less than half the real number.

Why: the error is not a fixed offset I could correct for, it is a measure of how
differently the two tokenizers were trained. `o200k_base` has learned merges
covering these Devanagari byte sequences and compresses them hard; Claude's
tokenizer does not compress them nearly as much on this text. The gap is widest
exactly where the two training corpora differ most — which is why no single
correction factor rescues it. It would have to be re-measured per language, per
format, per model, at which point I have rebuilt `count_tokens` badly.

Every error is negative — tiktoken undercounts on all five samples, by 24% to
48%. It flatters the budget in exactly the direction that hurts: the real number
shows up on the invoice, not in the estimate.

### 3. The cross-model delta

Same text, `claude-opus-5` vs `claude-sonnet-5`: **0.0% difference.** The counts
are identical on all five samples — 842/842, 3,525/3,525, 925/925, 1,930/1,930,
1,972/1,972. These two models share a tokenizer.

Implication: **0% here is not evidence that token counts are portable.** It is
evidence that these two particular models happen to agree, which is a fact about
this generation and not a rule. A count belongs to a (text, model) pair, and the
pairing breaks *across* generations rather than within them — Sonnet 5 produces
roughly 30% more tokens for the same text than Sonnet 4.6 did. A budget
calibrated last quarter on a previous-generation model is therefore wrong by
about a third, in the expensive direction, and nothing in the application code
changes to announce it. The rule I am adopting: re-baseline with `count_tokens`
on every model change, and treat a token budget as pinned to a model ID, never
to a text.

To actually see a non-zero delta, compare across generations rather than within:
`--models claude-opus-5,claude-haiku-4-5`.

### 4. Why UUID-dense log lines are the most expensive text

- **Incompressible.** BPE merges encode statistical regularity, and a trace ID
  like `4bf92f3577b34da6a3ce929d0e0e4736` has none — it is uniform random hex.
  The tokenizer finds no learned merges and falls back to short fragments.
  Measured on my own sample: `logline.txt` runs 1.63 chars/token against
  `prose.txt` at 3.35. The same number of characters costs **2.05× more**, and
  that is the floor, not the tail.
- **Semantically empty.** The model cannot reason about a trace ID beyond string
  equality. So I pay the highest per-character rate in the whole corpus for
  content that buys matching, not understanding. Prose at least converts tokens
  into meaning the model can operate on; a span ID converts them into a key.
- **They cluster.** One real line from my sample carries a trace ID, a span ID, a
  parent span ID, a request ULID, an ISO-8601 timestamp, an IP, a pod name and
  sometimes an image digest — every one high-entropy, all inside the same ~300
  characters. The worst case is not an occasional UUID buried in prose. The worst
  case *is* the normal shape of the line. 20 lines, 5,762 chars → 3,525 tokens,
  which is **176 tokens per line**.
- **Link to SENTINEL's Phase 2 retrieval budget.** At 176 tokens/line, a 1M
  context window holds only about **5,700 log lines** of this shape, and 1,000
  raw lines cost **$0.88** in input alone at Opus 5 rates. Every line I retrieve
  and do not use is paid for at the most expensive rate in the corpus, and it
  displaces a line I did need. That is why retrieval in Phase 2 has to be
  selective by construction rather than generous-and-filtered-later, and why
  Day 33's compaction work exists at all.



## Token-boundary visualization

Measured on the full file with the local Qwen 2.5 tokenizer — the only one of
the three that exposes token boundaries.

| measurement | devanagari.txt |
|---|---:|
| characters / bytes | 1,124 / 2,982 (2.65 bytes/char) |
| tokens (local) | 1,078 |
| boundaries landing mid-character | **293** |
| distinct characters torn apart | **293** (26% of the file) |
| tokens each torn character spans | **2** |
| tokens that are not valid UTF-8 alone | **586 of 1,078 (54.4%)** |

Decoded individually those 586 tokens produce U+FFFD, which is exactly why the
decoder needs `errors="replace"` — it is not defensive coding, it is the normal
case here. Averaged over the 928 Devanagari characters in the file, one character
costs **1.16 tokens** on the local tokenizer, against roughly 0.25 for an English
character in `prose.txt`.

**Finding that contradicts the expectation:** tiktoken `o200k_base` produced
**zero** mid-character splits on this same text — every one of its 435 tokens
decodes as valid UTF-8 standalone. Splitting is therefore not a property of
"Devanagari", nor of byte-level BPE in general. It is a property of one specific
tokenizer's learned merges. The lesson generalises the opposite way from how I
assumed it would: I cannot predict which tokenizer will shred a script, so I have
to measure the one I am actually calling.
